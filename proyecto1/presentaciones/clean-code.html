Planteamiento

La legibilidad como criterio de diseño.

El código de un juego se lee durante la revisión, la sustentación y las modificaciones posteriores. Un proyecto con Quadrille acumula reglas, capas y estados; si esos elementos no tienen nombres y límites claros, cada cambio exige reconstruir el contexto.

Verificación limitada

JavaScript no impide intercambiar dos coordenadas ni explica el significado de un argumento booleano. La claridad debe incorporarse en el diseño.

Crecimiento del proyecto

Cada mecánica nueva interactúa con las anteriores. Una función con varias responsabilidades concentra los defectos y dificulta las pruebas.

Explicación oral

Durante la sustentación, el código debe poder describirse en pocos minutos. Esa capacidad depende de la organización y no de la memoria del autor.

La legibilidad no es una propiedad opcional: determina si el código puede revisarse, probarse y modificarse sin depender del autor original.

Fuentes · Clean Code (Martin) y Refactoring (Fowler) La legibilidad se evalúa durante todo el proyecto

Estructura

Nueve ejemplos de refactorización.

Cada ejemplo ocupa dos diapositivas. La primera muestra una versión problemática y plantea una pregunta; la segunda presenta la versión refactorizada y explica el principio aplicado. Los casos provienen de situaciones habituales en un proyecto con p5.js y Quadrille.

Los temas son: nombres sin significado, constantes sin nombre, funciones con demasiadas responsabilidades, anidación excesiva de condiciones y argumentos booleanos sin contexto.

También se revisan la duplicación de funciones de dibujo, las coordenadas como valores primitivos, el estado global sin propietario y el acceso directo a la estructura interna de otros objetos.

Versión problemática

No se trata de ejemplos artificiales: corresponden a decisiones que aparecen en una primera implementación y que pueden corregirse sin cambiar el comportamiento del juego.

Versión refactorizada

Cada solución se inspira en una decisión real del proyecto. Mantiene el comportamiento y mejora la organización de las responsabilidades.

Ejemplo 01 / 09 · Problema

Nombres sin significado.

Los identificadores q, r, c, p y n no describen el papel de cada valor dentro del juego.

antes · tablero.js
let q, r, c, p, n;

function setup() {
  q = createQuadrille(17, 13).maze(color('#22375b'));
  n = 3;
}

function mousePressed() {
  r = q.mouseRow;
  c = q.mouseCol;
  if (q.isValid(r, c)) p = { r, c };
}

Pregunta

¿Qué información falta en estos nombres?

Conviene considerar qué representa cada variable, si el nombre se puede buscar en el proyecto y si otra persona podría modificarlo sin consultar al autor.

Pregunta

¿Cuántos lugares habría que modificar si el tablero cambiara de 36 a 40 píxeles?

Ejemplo 02 / 09 · constantes La solución se presenta en la diapositiva siguiente

Ejemplo 02 / 09 · Solución

Una única fuente de configuración.

después · config.js
const CONFIG = {
  cellLength: 36,
  reveal: { radius: 3.4, memoryAlpha: 0.66 },
  colors: {
    background: '#070b14',
    trail: [255, 206, 122, 26],
  },
};

function draw() {
  background(CONFIG.colors.background);
  drawingContext.globalAlpha = CONFIG.reveal.memoryAlpha;

  const radius = CONFIG.reveal.radius * CONFIG.cellLength;
  const trail = color(...CONFIG.colors.trail);
  drawQuadrille(board, { cellLength: CONFIG.cellLength });
}

Explicación

Cambios aplicados

Los valores se agrupan en CONFIG y cada uno recibe un nombre. Cambiar el tamaño del tablero, el radio de la luz o la paleta exige modificar un solo archivo. El valor 67 se eliminó porque no representaba una regla del juego.

Ejemplo 03 / 09 · Problema

Una función con demasiadas responsabilidades.

mousePressed valida la celda, calcula la ruta, mueve al jugador, actualiza la niebla, recoge ecos y abre el portal.

antes · mousePressed.js
function mousePressed() {
  const row = board.mouseRow;
  const col = board.mouseCol;
  if (!board.isValid(row, col)) return;
  if (board.isFilled(row, col)) { message = 'muro'; return; }
  if (!explored[row][col]) { message = 'niebla'; return; }

  const steps = board.path(player.row, player.col, row, col);
  if (steps.length === 0) { message = 'sin ruta'; return; }

  for (const step of steps) {
    player.row = step.row;
    player.col = step.col;
    explored[step.row][step.col] = true;
    fog.fill(step.row, step.col, color(6, 9, 18, 0));
    if (relic.row === step.row && relic.col === step.col) {
      relic.collected = true;
      score += 1;
    }
  }
  if (score === 3) portal.open = true;
}

Pregunta

¿Cuántas razones tiene esta función para cambiar?

Si se modifica el sistema de puntuación, la representación de la niebla o la condición de victoria, la misma función debe volver a revisarse.

Ejemplo 03 / 09 · responsabilidad única La solución se presenta en la diapositiva siguiente

Ejemplo 03 / 09 · Solución

Separación entre entrada y lógica.

después · Game.js
function mousePressed() {
  const cell = dungeon.cellAtPixel(mouseX, mouseY);
  if (!isWalkable(cell)) return;
  walk.planTo(cell);
}

function isWalkable(cell) {
  return dungeon.isFloor(cell)
    && reveal.isExplored(cell);
}

// Walk mueve y avisa; Game revela, cuenta y decide.
// La victoria no vive en el handler del mouse.

Explicación

Cambios aplicados

El controlador de entrada interpreta el clic y delega la validación en isWalkable. Walk se encarga del movimiento, mientras que Game actualiza la niebla, los ecos y la victoria. La función resultante se puede leer en tres líneas y cada responsabilidad queda en su clase.

Ejemplo 04 / 09 · Problema

Anidación excesiva de condiciones.

planTo acumula cinco condiciones antes de llegar al caso en el que la ruta es válida.

antes · Walk.js
function planTo(target) {
  if (target) {
    if (!target.equals(this.explorer.cell)) {
      if (this.dungeon.isFloor(target)) {
        if (this.reveal.isExplored(target)) {
          const steps = this.dungeon.path(
            this.explorer.cell, target
          );
          if (steps.length > 0) {
            this.plan = steps;
            return true;
          }
        }
      }
    }
  }
  return false;
}

Pregunta

¿Dónde se encuentra el caso normal y cuáles son las excepciones?

La estructura obliga al lector a recorrer toda la jerarquía para comprender una operación que debería ser directa.

Ejemplo 04 / 09 · anidación La solución se presenta en la diapositiva siguiente

Ejemplo 04 / 09 · Solución

Cláusulas de guarda.

después · Walk.js
function planTo(target) {
  if (!target) return false;
  if (target.equals(this.explorer.cell)) return false;
  if (!this.dungeon.isFloor(target)) return false;
  if (!this.reveal.isExplored(target)) return false;

  const steps = this.dungeon.path(
    this.explorer.cell, target
  );
  if (steps.length === 0) return false;

  this.plan = steps;
  return true;
}

Explicación

Cambios aplicados

Cada condición previa se resuelve con un retorno temprano. El camino exitoso queda al final y las reglas se leen en orden. La función conserva el mismo comportamiento y reduce la profundidad de anidación.

Ejemplo 05 / 09 · Problema

Argumentos booleanos sin contexto.

El segundo argumento de search() modifica el criterio de comparación, pero el llamado no explica cuál es ese criterio.

antes · win-check.js
const solved = board.search(solution, true).length > 0;

if (solved) {
  message = 'resuelto';
}

// Más adelante...
const strict = board.search(pattern, true);
const loose = board.search(pattern, false);

Pregunta

¿Qué significa true en este contexto y qué regla evalúa el juego?

El problema no está en la librería, sino en el punto de uso: la intención del juego queda oculta detrás de un valor booleano.

Ejemplo 05 / 09 · argumentos booleanos La solución se presenta en la diapositiva siguiente

Ejemplo 05 / 09 · Solución

Encapsular la intención en un método.

después · Puzzle.js
class Puzzle {
  isSolved() {
    return this.board.search(this.solution, true)
      .length > 0;
  }
}

if (puzzle.isSolved()) {
  hud.setMessage('Resuelto');
}

// El `true` sigue ahí, pero ahora vive
// dentro de una pregunta con nombre.

Explicación

Cambios aplicados

isSolved() expresa la regla del juego y concentra la llamada a search() en un solo lugar. Si cambia el criterio de comparación, la modificación se realiza en el método y no en cada punto de uso.

Ejemplo 06 / 09 · Problema

Duplicación de funciones de dibujo.

Los efectos del eco y del portal repiten el halo, el rombo y el recorrido de las capas con parámetros distintos.

antes · efectos.js
const relic = function (o) {
  noStroke();
  for (let i = 3; i >= 1; i--) {
    fill(116, 230, 255, 10 + 6 * i);
    circle(0, 0, 10 + i * 8);
  }
  fill(190, 250, 255);
  quad(0, -8, 8, 0, 0, 8, -8, 0);
};

const portal = function (o) {
  noStroke();
  for (let i = 3; i >= 1; i--) {
    fill(255, 196, 96, 8 + 3 * i);
    circle(0, 0, 12 + i * 10);
  }
  fill(255, 196, 96);
  quad(0, -10, 10, 0, 0, 10, -10, 0);
};

Pregunta

¿Qué parte del código se repite y qué parte cambia entre ambos efectos?

La duplicación obliga a corregir dos veces el mismo defecto y dificulta añadir un tercer efecto.

Ejemplo 06 / 09 · duplicación La solución se presenta en la diapositiva siguiente

Ejemplo 06 / 09 · Solución

Composición de efectos.

después · efectos.js
const halo = (rgb) => function (o) {
  noStroke();
  for (let i = 3; i >= 1; i--) {
    fill(rgb[0], rgb[1], rgb[2], 8 + 4 * i);
    circle(0, 0, o.cellLength * (0.3 + i * 0.2));
  }
};

const diamond = (rgb) => function (o) {
  noStroke();
  fill(rgb[0], rgb[1], rgb[2]);
  const r = o.cellLength * 0.2;
  quad(0, -r, r, 0, 0, r, -r, 0);
};

const stack = (...fx) => function (o) {
  fx.forEach((f) => f.call(this, o));
};

const relic = stack(
  halo([116, 230, 255]),
  diamond([190, 250, 255])
);
const portal = stack(
  halo([255, 196, 96]),
  diamond([255, 196, 96])
);

Explicación

Cambios aplicados

halo y diamond reciben el color como parámetro y devuelven una función de dibujo. stack combina esas funciones y produce el efecto completo. La variación queda en los argumentos y la lógica de dibujo se escribe una sola vez.

Ejemplo 07 / 09 · Problema

Coordenadas como valores primitivos.

La función path recibe cuatro números en un orden que el lenguaje no puede verificar.

antes · path.js
function path(row1, col1, row2, col2) {
  // ...
}

const steps = path(
  playerRow, playerCol,
  targetRow, targetCol
);

// En otro lugar, sin querer:
const wrong = path(
  targetCol, targetRow,
  playerCol, playerRow
);

Pregunta

¿Qué impide intercambiar row y col al llamar a la función?

Nada en JavaScript detecta el error. La ruta resultante puede ser incorrecta sin producir una excepción, y el defecto aparece lejos del punto de origen.

Ejemplo 07 / 09 · valores primitivos La solución se presenta en la diapositiva siguiente

Ejemplo 07 / 09 · Solución

Un objeto de valor para las celdas.

después · Cell.js + Dungeon.js
class Cell {
  constructor(row, col) {
    this.row = row;
    this.col = col;
  }

  equals(other) {
    return this.row === other.row
      && this.col === other.col;
  }
}

path(from, to) {
  return this.known
    .path(from.row, from.col, to.row, to.col)
    .map(({ row, col }) => new Cell(row, col));
}

Explicación

Cambios aplicados

Cell agrupa fila y columna, y path recibe from y to. La comparación y la generación de claves quedan centralizadas, y el llamado ya no depende de recordar el orden de cuatro números.

Ejemplo 08 / 09 · Solución

Encapsulación del estado en una clase.

después · Game.js + main.js
class Game {
  constructor(hud) {
    this.hud = hud;
    this.state = 'playing';
    this.startRun();
  }

  handleClick(x, y) { /* ... */ }
  update(dt) { /* ... */ }
}

let game; // el único global que p5 necesita

function setup() {
  game = new Game(new Hud());
}

Explicación

Cambios aplicados

Game concentra el estado y las transiciones entre playing y won. Las dependencias se reciben por el constructor y el único global es el punto de entrada que exige p5.js. La lógica queda separada de la interfaz y puede probarse con mayor facilidad.

Indicador de configuración

El radio de la linterna se puede cambiar en un solo archivo y el juego continúa funcionando sin buscar valores por todo el proyecto.

Indicador de mantenibilidad

Una mecánica se puede explicar sin abrir su archivo: se conocen sus entradas, sus salidas y la clase que asume la responsabilidad.

Problemas frecuentes

Tres problemas adicionales.

Método centrado en otro objeto

Un método utiliza más datos de otro objeto que los propios. La regla probablemente pertenece al objeto del que provienen los datos.

Listas de parámetros extensas

Una firma con seis argumentos indica que los valores forman una estructura que debería tener nombre.

Cambios dispersos

Si modificar un detalle exige editar varios archivos, la decisión está distribuida y conviene centralizarla.

Un proyecto mantenible localiza sus decisiones y permite explicar el comportamiento a partir de los nombres y de las responsabilidades de sus clases.
